# Real integration readiness

Phase 10 documents the existing boundaries; it does not implement a backend. The authoritative frontend interfaces are `src/repositories/contracts.ts`. Real adapters belong under `src/services/api/` and must be injected through the composition root in `src/repositories/index.ts`. UI must continue to use query hooks and `RepositoryProvider`.

`RequestOptions.signal` exists on repository reads; adapters must forward cancellation and avoid treating cancellation as a user-visible failure. Mutations currently do not expose that option. Map API responses to validated domain schemas at the adapter boundary; do not send raw API DTOs to components.

## Address boundary

There is **no `AddressRepository` interface today**. `useAddressStore` in `src/stores/checkout.ts` is the local validated address-book boundary, with save/select/default/remove operations. Demo guest/account snapshots own its current contents.

Real synchronization will require a deliberately designed address contract: authenticated list/create/update/delete/default selection, stable server IDs, ownership, address validation, conflict/retry behavior and logout isolation. Decide whether guest addresses stay local and how a user approves merging them. Do not describe this future interface as already implemented.

## Commerce authority and synchronization

- `src/features/cart/useCartQuote.ts` and `pricing.ts` currently build quotes from injected product/store repositories; Checkout reuses that boundary. There is no real quote, stock reservation, payment or delivery API.
- The backend must atomically validate store, fulfillment, inventory, variant quantity, prices, age-related sales rules and delivery eligibility. Client-calculated totals are display/checking inputs, not authority.
- Money is integer minor units; current checkout accepts UAH. Quantity is a count of an identified serving variant, with explicit ml/g amounts. Preserve product/variant/store identity in transfers and retries.
- Order idempotency must survive process restart, timeouts, multiple clients and payment callbacks. The local mock guarantee is insufficient for those conditions.
- Store switching currently reuses `prepareCartTransfer`: unavailable/over-limit lines remain visible and block checkout. Preserve this behavior with real offers and stock responses.
- Favorites, cart and guest merges need a server synchronization policy before multi-device support. Current workspace snapshots prevent repeated local merges; they are not a distributed transaction.

## Authentication and error policy

Native production credentials require a secure platform-specific `SessionPersistence` implementation. Production Web should use an appropriately protected backend-managed session (for example HttpOnly cookies with CSRF protection where needed), not localStorage bearer tokens. Never persist or log OTPs, tokens, private order payloads or card data.

Define typed adapter errors for invalid input, expired challenge, rate limit, unauthenticated/forbidden, unavailable item/store, idempotency conflict and temporary transport failure. Translate them into the existing Ukrainian error/retry states without raw exceptions. Do not make an authorization failure look like a retryable network error. Existing query reads retry once; mutations do not automatically retry. A deliberate order retry reuses its idempotency key while the payload is unchanged.

Keep account IDs in query keys, reject late responses after owner changes, clear account caches on identity transitions and reset owner-specific form state. Server authorization remains mandatory even though the UI guards private routes.

## Decisions before implementing adapters

1. Agree on stable IDs, DTO schemas, API versioning, timestamp/timezone rules and pagination.
2. Approve the auth/session/guest-order policy and secure storage implementations.
3. Select authoritative catalog, prices, stock, tap-list, order, delivery, loyalty and POS/CRM sources.
4. Specify order/quote/payment idempotency and failure reconciliation.
5. Define address and guest/account synchronization with explicit conflict decisions.
6. Supply approved public API/map/image hosts and a production hosting/deep-link strategy.
7. Inject real repositories in contract tests and test unauthorized reads, cancellation, malformed data, retries and identity switching before changing production readiness.

Setting `EXPO_PUBLIC_API_URL` alone never performs these steps. Production remains blocked until adapters, credentials, identifiers and the release requirements are implemented and verified.
